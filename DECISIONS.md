# Decisions

- (UI refresh, 2026-10-18) Use generated Higgsfield 2048px transparent geometric portraits in the web UI, recoloured from coral masters with CSS to preserve saved shape × colour identities. Keep original PNGs, optimized WebP assets and provenance together; fall back to the existing SVG renderer when an asset fails. The event-driven office keeps its animated pixel sprites.
- (UI refresh) Group navigation in a responsive sidebar; use subdued dark surfaces, lilac primary actions and restrained rainbow branding. Load the computer view on demand so terminal code does not slow down the agent overview.

One line each: decision, reason.

- Repo lives in `NorthBots/northbot/` next to the build prompt, so the prompt file stays out of the repo.
- Node 22 is the target (Docker images, CI, `engines`); local dev also runs on Node 24, which is compatible.
- zod 3 (not 4) with `fastify-type-provider-zod@4`, because that pairing gives zod validation + OpenAPI generation from one schema.
- Workspace packages export TypeScript source (`exports: ./src/index.ts`); the server is bundled with tsup, which inlines them, so no per-package build step.
- The first migration is a hand-written `CREATE EXTENSION vector`, and later migrations are generated by drizzle-kit.
- Migrations run on boot under a Postgres advisory lock, so several server instances can start together safely.
- Web container is nginx serving the Vite build and proxying `/api/*` (prefix stripped) and `/v1/*` to the server, which keeps one origin for cookies.
- Server tests run against the real compose Postgres (no mocks for the DB), one file at a time.
- Acceptance scripts are bash; on Windows they run under Git Bash.
- `events` has a `workspace_id` column beyond the spec's list, because every read is scoped to one workspace.
- Live event delivery uses a Postgres trigger + `NOTIFY nb_events`, so events written by any instance (or SQL) reach every WebSocket.
- Event replay `?from=<id>` is inclusive, so "replay from id 50" includes event 50.
- Only `user.note` events are client-writable over HTTP; all other types are written by the server.
- Argon2id via `@node-rs/argon2` (prebuilt binaries, no node-gyp) with OWASP parameters (19 MiB, t=2).
- Sessions: a random 32-byte token sits in an httpOnly cookie, and only its sha256 is stored.
- Passkey login uses discoverable credentials (no email needed). Challenges live in Postgres and are single-use, 5 min TTL.
- Vault subkeys are derived per workspace with keyed BLAKE2b over the master key. libsodium is loaded via its CJS build.
- "Use in sandbox" goes through a `SecretSink` interface. M1 ships an in-memory sink, and M3 wires the real container sink.
- A software ES256 WebAuthn authenticator (`apps/server/src/auth/soft`) drives passkey tests and is reused for vault signing in M11.
- Acceptance logic is written as Node `.mjs` scripts called from `mN.sh` (fetch + ws), which is more robust than curl for cookies and WebSockets.
- Provider adapters use the official SDKs (`openai`, `@anthropic-ai/sdk`, `@google/genai`) and are tested offline against local mock HTTP servers.
- Anthropic: never send `temperature`/`thinking` budgets (current Claude models reject them); `effort` is the control. Server-side refusal fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) is on by default for the first-party API and off when a custom `baseUrl` (proxy) is set.
- Assistant turns carry `raw` provider content; the Anthropic adapter replays it unchanged on the same provider+model, so Claude thinking blocks stay valid (agent loops must be append-only and keep the system prompt frozen).
- Default aliases: `northbot-smart` = claude-opus-5-5 > gpt-4.1 > gemini-2.5-pro; `northbot-fast` = claude-haiku-5-5 > gpt-4.1-mini > gemini-2.5-flash. Targets without a vault key are skipped.
- Non-Anthropic prices in the built-in table are best-effort defaults; every row can be overridden in `settings.llm.pricing`. Unknown cloud models are priced high ($10/$50 per M) so caps still bite.
- Budget caps are checked before each call against `llm.call` event costs: spent >= cap blocks. A single call can overshoot a cap; the next one is refused. Scopes: workspace/day, API key/day, agent/day (workspace timezone), task (whole task).
- PII redaction (email, CPF, CNPJ, Luhn-valid cards, phones) runs only for `cloud` providers and is reversed in replies; raw provider turns are dropped when redacting because they hold unredacted text.
- The fake provider is stateless: script turn i answers the request holding i assistant messages, so agent runs replay identically.
- Router fallback triggers on any provider error (network, 4xx, 5xx); streams fall back only before the first chunk is emitted.
- /v1 routing hints: `x-northbot-{privacy,agent-id,task-id,task-budget-usd}` headers or `metadata.northbot_*`. Errors use the OpenAI error shape: 402 budget, 403 privacy, 404 model, 502 all providers failed.
- `/v1/responses` is basic: non-streaming text in/out (streaming returns 400 pointing to chat completions).
- API keys are `nb_` + 24 random bytes; only sha256 is stored; shown once at creation; scope `llm` required for /v1.
- The `agents` table landed in M2 (needed for per-agent budgets) with the spec's columns.
- The server reaches agentd through `docker exec -i ... bridge.mjs` (JSON lines over stdio), not the network. That works the same from the host (Docker Desktop cannot route to container IPs) and from the server container, and leaves zero listening ports on the agent's network.
- agentd runs as root on a root-only unix socket (0600) plus a per-boot token readable only by root. Shells run as uid 1001 `agent` via node-pty, so the agent's own terminal cannot reach agentd or read the browser profile (`/home/agent/.northbot-browser`, root 0700).
- Chromium runs headless with `--no-sandbox` (Playwright's default in containers). The container itself is the sandbox: cap-drop ALL (plus SETUID/SETGID/CHOWN/DAC_OVERRIDE/FOWNER/KILL for agentd), no-new-privileges, pids/memory/cpu limits.
- Egress: each agent gets its own `internal: true` Docker network, so there is no route out. A shared `egress` proxy container joins every agent network (alias `egress`). Agents use HTTP(S)_PROXY with per-sandbox credentials (only a sha256 is stored). The proxy writes `egress` events straight to Postgres. HTTPS is a CONNECT tunnel: host and port are logged, content is never seen.
- One Docker network per agent means the default Docker address pools cap a host at about 30 agent computers. Raise `default-address-pools` in the daemon config for more.
- Hibernate is `docker pause`: processes, shells and open tabs survive as they are. Snapshot is `docker commit` plus a copy of the home volume (the computer is paused during the copy).
- Command timeouts use coreutils `timeout -k 2`, where exit 124 means timed out. Output is capped at 1 MiB per stream. Logged commands and output previews are run through `scrubSecrets`.
- Vault "use in sandbox" passes the value through the docker exec environment, never on a command line, so it never reaches events. `env` mode writes ~/.northbot/secrets/NAME and an export line in ~/.bashrc.
- The server container runs as root with the Docker socket mounted, which is required to manage agent computers. That makes it as trusted as the Docker host.
- Take over: the live screen WebSocket forwards mouse and text input as CDP `Input.*` only after a `takeover` message. Takeover and release are events, and the agent runtime (M4) pauses tool calls while a human has control.
- Node 22 in the agent image is copied from the official node image (no curl|bash installers). Playwright/node-pty versions resolve at image build (no lockfile inside the image).
- The agent runtime is a pure package (`packages/agent-runtime`) behind a `RunnerDeps` interface. The server wires models, computers, approvals, rules, the ledger and events into it, so the loop is unit-tested without Docker or Postgres.
- Tool calls are classified by heuristics: commands by program, flags and redirections (unknown programs = write; compound commands take their riskiest part). Browser clicks are classified by the target element's visible text. Kind priority: spend > send > login > delete > write > read.
- Autonomy defaults: suggest_only blocks everything but reads; ask_first asks for all non-reads (the spec default); act_within_limits allows writes; autonomous also allows sends. Delete, spend and login always ask unless a rule allows them. Rule precedence: block > allow > ask > autonomy default.
- "Always allow" in the inbox becomes an agent-scoped rule for the same kind, tool and targets (or the exact summary when there are no targets).
- Plain-language rules are compiled by a model call to the `northbot-fast` alias into JSON that is zod-validated before storage. JSON rules can also be posted directly.
- Injection shield: all tool output is wrapped in `<tool_output trust="untrusted">`, and fake closing tags are neutralised. Outbound actions (send/spend/login) must be (1) asked for by the original instruction (verb check) and (2) aimed only at hosts/addresses in the instruction or in an allow rule. Otherwise they are blocked and the model is told not to work around it. Text that looks like an injection taints the task, and a tainted task needs a human for every outbound action.
- Self-critique is one extra model turn ("check your work against the goal") before accepting a final answer. Verification is a separate model call that labels each claim verified/inferred/guessed. Planner and verifier models can differ from the worker (modelPolicy.planner/verifier).
- Task state (messages, plan, counters) is saved after every step, and unfinished tasks resume on boot. Messages are append-only, and provider raw turns are kept for replay.
- Idempotency key = sha256(taskId | tool | canonical args) for every non-read action, held in the `actions` ledger. A key already done returns its stored result; one that started but never finished is reported as "outcome unknown, check first" and is not re-run; a failed one may be retried.
- Failure recovery: each failed tool call tells the model to try a different method. After 3 failures in a row the task escalates (status `blocked`, agent `blocked`, event `task.escalated`).
- Long jobs: after planning, the estimate is steps × 2 × the agent's average past call cost (default $0.01). Above TASK_CONFIRM_ABOVE_USD (default $1) it waits for an approval before starting.
- Kill switch: aborts local runners first, sets `workspaces.kill_switch_at`, marks active tasks killed, cancels their approvals, TERMs every exec'd command in the workspace's computers (the `timeout -k 2` wrappers) and emits `killswitch.engaged`, which other server instances act on. New tasks get 409 until it is released.
- Approval waits listen for `approval.decided` events (NOTIFY, so any instance) plus a 5 s poll as a safety net.
- Server tests use a separate `northbot_test` database on the compose Postgres, so the running server never resumes test tasks.
- Mood engine: a pure `computeMood` in packages/shared with a fixed precedence (worried > overwhelmed > impatient > grumpy > confused > annoyed > embarrassed > sad > proud > sleepy > content) and decay windows (proud 30 min, sad 60 min, ...). Causes are first-person and never blame the human.
- The events behind moods: `agent.interrupted` (cancel / take over / office pick-up), `feedback.correction`, `instruction.contradiction` (an allow and a block rule that can match the same action), `idea.rejected` (M7), plus existing task/approval/egress/budget events.
- The MoodService recomputes on each agent event (150 ms debounce) and once a minute for time-based moods. It writes `agent.mood` only on change and notifies only for impatient/worried/overwhelmed/grumpy/confused. Notifications raised in quiet hours get a later `deliver_at` (default 22:00–08:00 in the workspace timezone; `null` turns quiet hours off). There is a global and a per-agent mood off switch.
- Avatars are an original layered SVG set (5 bases × 6 colours × 7 accessories, one face per mood plus dizzy/hearts), generated as strings in packages/shared so the web app, the office and exports share them. The alt text gives the plain-language equivalent.
- Name rules (`checkAgentName`): 2–12 chars, letters/numbers/space/'/-, and a blocklist of brands, real people, famous characters and offensive words with leetspeak normalisation (short words match whole words only). Uniqueness is case-insensitive per workspace (DB index on lower(name)). Quick-created and human-renamed names are locked; self-chosen ones are not.
- Self-naming asks `northbot-fast` for three candidates, validates each, retries up to 3 times with the rejected names listed, then fills from a built-in cozy list.
- New agents default to modelPolicy { model: northbot-smart, planner: northbot-fast, verifier: northbot-fast }. The hatching personality maps to persona text, and "check in rarely" maps to act_within_limits (otherwise ask_first).
- The first task after hatching asks for read-only commands only (`uname -a`, `ls -la ~`), so it finishes without approvals in about a minute.
- Fake models can answer by role: `fake.match` picks a reply when the system prompt contains a phrase (namer, planner, verifier, rule compiler, chat).
- Chat: "Ask" streams a reply over SSE (no tools; attached text files under 50 KB are inlined as untrusted <attachment> data). "Do it" turns the message into a task. Attachments go to ~/inbox via `Sandbox.writeFile` (docker putArchive, owned by the agent), and the task's report is posted back to the thread. Files are stored in Postgres (bytea, 10 MB cap) and always downloaded as attachments, never rendered on our origin.
- E2E tests use Playwright against the compose stack (http://localhost:8080) with scripted fake models set through the API after sign-up.
- (User request, 2026-10-18) Avatars are now geometric: 10 shapes (circle, square, triangle, diamond, pentagon, hexagon, octagon, star, capsule, semicircle) × 15 colours, with two dot eyes. Moods show through eye placement/squash and a small mark (sparkle, sweat drop, z's, ?, !!, blush, heart). This replaces the earlier blob/cat/robot/plant/ghost set and accessories; old avatars are mapped to the closest shape/colour.
- Each look (shape + colour) is unique per workspace (DB unique index on workspace + shape + colour). Hatching or editing to a taken look returns 409 `look_taken`; quick create and team hatching pick the next free look and retry on a race. Duplicates from before the index lose their look in the migration and get a free one at startup (`normalizeLooks`). There are 150 looks, so at most 150 agents per workspace.
- (User request) The office (M8) will draw agents as pixel-art sprites generated from the same 10 shapes and 15 colours, with several animations (idle, walk, carry, sleep, bounce, dizzy, ...).
- (User request) The UI is dark: blacks and grays for surfaces and text, with rainbow accents (title, a divider bar, primary buttons, selected items, active nav). Agent colours stay vivid so bots are easy to tell apart. Tailwind tokens were remapped (cream=page black, panel/peach..butter=gray steps, ink=light text).
- The tool layer decodes `\uXXXX` in anything typed, so invisible-character patterns are built from code points (`String.fromCharCode`) and the source files contain no invisible characters.
- (User request) Fun status animations on avatars, all CSS and switched off under reduced motion. Working: squash-and-bounce inside a spinning rainbow ring, orbiting sparkles and a typing bubble. Waiting: sway with a slow "…". Resting/idle: breathing. Blocked: a small shake. Pages that show an agent poll its status every 3 s so the animation follows the work. The office (M8) gets matching pixel-sprite animations.
- The server bundle inlines @northbot/* packages, so their npm dependencies must also be server dependencies. `test/bundle-deps.test.ts` enforces this (a missing `yaml` once broke boot with "Dynamic require of process").
- The local hash embedder uses 1024 dims with two buckets per feature and a consistent light stemmer (a single "shop"/"close" collision once erased both words). The model name is part of each stored row, and stale rows are re-embedded at startup.
- Memory learning and skill drafting run after a task is done, with the cheap helper model (`planner`, default `northbot-fast`). Failures there never fail the task. Quick-created agents now default to planner/verifier = northbot-fast like hatched ones.
- TaskService claims a task in `running` before any await, so idle() and duplicate starts see it at once.
- Notifications are compared with the database clock (`deliver_at <= now()`), not the Node clock.
- When learning after a finished task is over (memory + skill drafting), the server writes `task.learned` (facts kept, whether a skill was drafted and why). Acceptance waits on it instead of sleeping.
- Web: Memory page (search by meaning, filter shared/per agent, add, edit, forget with derived facts, export download, import upload) and Skills page (review cards with files, diff, scan findings, test-run output, rights; approve / edit-then-approve / reject; approved library with versions and rollback). Finished tasks have a "Make this a skill" button (demonstrated routine).
- The command classifier now looks through wrappers (env, xargs, timeout, nohup, nice, ...) to the command they run, classifies awk `system()` by what it runs, and treats sed `w`/`e`, `sort -o`, `uniq IN OUT` and `find -fprint` as writes (`-ok` as delete). Before, `env rm -rf ~` and `awk 'BEGIN{system("rm ...")}'` counted as reads. A `>` inside a quoted awk program still counts as a write: a false alarm is the safe direction.
- A skill's description and search embedding follow its active version (approve, edit-then-approve, rollback).
- Agents reach NorthBot features (letters, idea bin) through extra tools in the agent loop, not through an `nb` CLI calling the server from the computer. The computer keeps no route into the server, and every such tool has a fixed action kind that goes through permissions.
- (M7) The mail agent is a built-in server service, not an agent row with a computer. It scores every agent (skill match 0.5, private-memory match 0.25, past success 0.15, minus load 0.15 and today's spend share 0.1), and its confidence is relevance (best skill or memory match / 0.6) times how clearly the best beats the runner-up. Below 0.5 the letter goes to the workspace coordinator (setting `coordinatorAgentId`), or to a human (`needs_human` + a note) when there is none. Every routing decision is a stamp on the letter and a `letter.routed` event.
- (M7) Letter types: request, question, idea and urgent become a task for the handler (urgent also notifies humans); an FYI becomes a private memory of the handler instead of work. When a letter's task ends, its report goes back to the sender as a reply letter; replies to agents become their memory, never new work, so agents cannot ping-pong letters forever.
- (M7) Work that comes from another agent (its letters, or board tasks the coordinator hands out) starts as a tainted task: the injection shield then asks a human before any outbound action. Agent letters also tell the recipient the content is a coworker's request, not the user's orders.
- (M7) Agent tools: `send_letter` counts as a write (it makes another agent spend), `toss_idea` as a read (it only adds a note to NorthBot's bin).
- (M7) Rooms: only human messages start agent turns (at most 4 speakers per message), so agents never chat in an endless loop. @mentions pick speakers; otherwise the room's coordinator returns JSON with speakers and board tasks. Room text from agents is wrapped in <room_message> tags and treated as data. A room stops at its cost cap (summed from the model calls it makes) and posts one note; a human can interrupt a round at any time.
- (M7) Idea bin triggers: after a date, a new memory that contains all the trigger's key words (or is ≥0.6 similar), or an event type (optionally containing text). The bin-picker runs every `BIN_PICKER_INTERVAL_HOURS` (168 = weekly) in the server until M9 turns it into a real schedule, plus `POST /ideas/pick` to run it now. Ideas expire after the workspace's `ideaBinDays` (default 30).
- (M7) Talks run as a stage machine stored on the talk row (brief → prepare → present → qa → challenge → decide → record → learn → done), resumable after a restart. Helper turns (questions, votes, quizzes) use the cheap planner model. The dissenter defaults to the first listener. Q&A takes one question per listener plus human questions, answered first come, first served (at most 6). A listener's memory is updated only when their one-question quiz answer is ≥0.35 similar to the decision record; the fact links to the `talk.decided` event (`sourceEventId`, now exposed on memories).
- React effects must have block bodies (ESLint rule): an expression body returns its value as the cleanup, and newer Chromium returns a Promise from `scrollIntoView`, which crashed the chat and room pages on navigation.
- (M9) Scheduling uses Croner for timezone-aware occurrences, locked Postgres rows for claiming, and pg-boss for delivery. A persisted outbox closes the commit/enqueue gap. Every automatic occurrence has a stable idempotency key; retries reuse the task checkpoint and action ledger.
- (M9) Per-day budgets reserve funds while a run is active under the parent schedule lock, including when overlap is allowed. The task budget, timeout and workspace kill switch remain independent limits. Schedule approval covers the target, prompt, inputs, skill version and action kind; edits invalidate it.
- (M9) System routines are visible, pausable and protected from deletion. Nightly backup remains paused until M12 wires the deployment backup runner; a premature run fails explicitly. The old ad-hoc idea picker interval was replaced with its weekly schedule.
- (M10) MCP uses the official TypeScript SDK on both sides. Stdio travels over Docker exec streams as uid agent, with separate stderr discarded; no MCP command executes on the host. HTTP uses Streamable HTTP. Both reconnect and compare the complete schema/description/version hash before every call.
- (M10) Assignment approval is separate from M4 action approval. Only approved, scanned descriptions reach model context. Ask policies request their own inbox approval even for read tools; block policies always refuse. A changed classification during a task requires a new task. NorthBot's stateless endpoint authenticates every request against a revocable scoped API key, rejects foreign browser origins, and limits requests by token hash.
- (M11) Private passkeys use software ES256 WebAuthn inside the vault. Browser get() requests cross a root-controlled agentd binding carrying the actual frame origin; only the main frame may request signing. Exact site/RP matching, live-page verification, current grants and M4 login policy precede signing. Reserved signing keys cannot be injected into a computer or resolved as model/MCP tokens.
- (M11) Memory text is authenticated ciphertext under agent/shared subkeys; vectors remain queryable. Idea triggers now read decoded memory through MemoryService with the idea agent's visibility. Legacy text is encrypted at startup without changing facts, embeddings or exports.
- (M11) Encrypted persistent home volumes are an opt-in gocryptfs driver. It uses a host FUSE device and root-only RAM key handoff, never Docker environment configuration or event payloads. Existing computers are not silently migrated. The real-driver test checks backing-volume ciphertext and persistence after stop/unlock. FUSE needs SYS_ADMIN and an unconfined AppArmor profile; keep the default driver on hosts where that tradeoff is unacceptable.
- (M11) Data labels propagate from files/memory to the receiving agent; destination allowlists intersect as sensitive data accumulates. Restricted agents use local models and cannot send data to unapproved hosts through commands, MCP or the egress proxy. Audit recordings use redacted activity summaries and retain no raw screenshots.
- (M12) The Windows companion lives in `companion/` (Go, one dependency: coder/websocket). It only dials out; the person at the computer sets the power level and the shared folders and apps, and the server cannot widen them (the server also refuses early, as defence in depth). Commands run one at a time, in order. Every acting command leaves a screenshot in the audit log (stored as a file plus a `companion.screenshot` event). Devices are off for every agent until a person assigns one agent and turns it on; agents then get `desktop_look` (read) and `desktop_act` (write) tools that go through the normal permission system. The workspace kill switch also stops companions.
- (M12) Backups run on the host (`northbot backup`: `pg_dump -Fc` plus `.env` with the vault key, in one mode-600 archive), scheduled nightly by `install.sh`, not inside the app: the app container has no business holding database dumps and the key together. The in-app backup routine stays off.
- (M12) `northbot update` backs up first, tags the running images `:rollback`, rebuilds, and switches back if the health check fails within two minutes. Schema changes are not rolled back automatically; the message names the pre-update backup to restore.
- (M12) Images have explicit names (`northbot/server:latest` etc.) so updates can be tagged and rolled back. Production binds Postgres and the API to 127.0.0.1 (`BIND_ADDR`); only Caddy (HTTPS) is public.
- (M12) Operations: canary checks every 10 minutes include a canary task through the real agent loop with a scripted model and an in-memory computer (no cost, no side effects). Failed tasks and failed scheduled runs land in a dead-letter queue (retry creates a new task or run). The public status page shows instance health only.
- (M12) The store operator pack is installed through the API (`POST /packs/store-operator/install`), idempotently; agents carry `persona.pack`. Name or look clashes get a numbered name and a free look. Its integrations sit behind interfaces with deterministic fakes; the simulated day runs on fakes unless `real: true` and the vault holds the store secrets.
- (Review, M3 fix) The egress proxy now refuses private destinations (loopback, RFC 1918, link-local and cloud metadata, CGNAT, IPv6 ULA and link-local) and connects to the address it checked. Before, an agent could reach the compose network (the database, the server) through it. `EGRESS_ALLOW_PRIVATE=true` turns the check off for local experiments.
- (Review) Security and vault routes answer caller mistakes with 400 (a scoped error handler) instead of 500.
- (Review, M3 fix) Each agent network gets an explicit /28 from `SANDBOX_SUBNET_POOL` (default 10.213.0.0/16, 4096 agents). Docker's default pools give every network a /16 or /20 and ran out after about 30 agent computers, which broke installing the store pack on a busy instance.
- (M12) `northbot update` without `--source` pulls only when the checkout has an upstream branch; otherwise it rebuilds the files already in place.
