# Deployment and Backups

The installer targets a fresh Ubuntu 22.04/24.04 host you administer, with a domain pointing to it. It generates private credentials and places the web app behind Caddy HTTPS. Public VPS/domain, Let's Encrypt, systemd and nightly cron behavior still need real-host validation; the automated install check uses a clean Ubuntu 24.04 container and Caddy's local CA.

## Install

Clone the repository and review the installer before running it with root privileges:

```bash
git clone https://github.com/matnorte/NorthBots.git
cd NorthBots
sudo ./install.sh --domain bots.example.com --email you@example.com
```

Replace the domain/email with yours. Make DNS and inbound HTTPS/HTTP routing available to the host. Use this installer on a fresh machine, not as an unreviewed modification of a shared server with unrelated services.

The installer installs Docker when needed, copies the source to `/opt/northbot`, generates a vault master key/database password in `.env`, builds images, starts Compose with Caddy, creates the initial account, installs the `northbot` CLI and schedules a nightly backup. The first password is stored privately in `/opt/northbot/first-login.txt`; retrieve it locally and keep it out of issues, screenshots and Git. Re-running the installer preserves existing keys and data.

The installed API/database bind to loopback. The server has root/Docker-socket control to provision agent computers, so host administrators and the application server are inside the trust boundary. Keep the host patched and restrict access to its Docker service.

## Daily commands

```bash
sudo northbot status
sudo northbot backup
sudo northbot restore /path/to/backup.tar.gz --database restore_check
sudo northbot update --source /path/to/reviewed/NorthBots
```

Backup produces a private archive containing the database and `.env` recovery material. Keep a protected off-host copy. A database backup is not a backup of every agent home volume; retain/export those separately where required. Test restoring to a fresh database before relying on your recovery plan.

Restoring over the live database requires `--yes`. Do that only after taking a current backup and deciding which data may be replaced. Archive extraction accepts allowlisted members into fixed private files and validates the dump before destructive steps.

## Updates and rollback

Use a reviewed source checkout. Update backs up first and preserves current image identities, runtime Compose/Caddy settings and agent-network attachments. Failed source/build/start/health stages trigger rollback. Existing computers regain their egress attachments after rollback.

**Database schema rollback is manual** using the pre-update backup. Image rollback alone cannot reverse arbitrary migrations. Read migration changes before updating a live instance.

## Key configuration

| Setting                   | Purpose                                                     |
| ------------------------- | ----------------------------------------------------------- |
| `NORTHBOT_MASTER_KEY`     | Base64-encoded 32-byte recovery/encryption key; preserve it |
| `RP_ID`                   | Bare relying-party hostname                                 |
| `WEB_ORIGIN`              | Exact browser origin, including HTTPS                       |
| `COOKIE_SECURE`           | Secure cookies; true for HTTPS deployment                   |
| `POSTGRES_PASSWORD`       | Private database password generated by installer            |
| `SANDBOX_SUBNET_POOL`     | Per-agent network pool; default `10.213.0.0/16`             |
| `SANDBOX_DISK_ENCRYPTION` | Optional encryption for new agent homes                     |
| `SCHEDULE_MIN_INTERVAL_S` | Minimum interval, default 300 seconds                       |
| `CANARY_INTERVAL_MINUTES` | Canary frequency, default 10 minutes                        |

Compose explicitly forwards a set of server environment variables. A setting supported by the server but absent from Compose must also be wired into the deployment configuration; merely adding any arbitrary variable to `.env` does not forward it into a container. See [server configuration](../../apps/server/src/config.ts), [Compose](../../docker-compose.yml) and [deployment CLI](../../deploy/northbot).

`.env`, `backups/` and `first-login.txt` must never be committed. Build contexts exclude private runtime files; older local builder caches may still contain material from before those exclusions and should remain private.
